# Deployment

Section 6 asks for a free/free-tier deployment, or a documented constraint plus a
reproducible Docker path. This repo does both: the Docker Compose setup below is
what was actually run and verified for the demo, and Section 2 ships a Render
Blueprint (`render.yaml` at the repo root) that stands the same two images up on
a free tier with one click, so a deployment can be live in minutes without paying
for anything.

## 1. Docker Compose (verified, reproducible anywhere Docker runs)

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
docker compose up --build
```

What that gives you:

| Service | Image | Port | Start-up behaviour |
|---|---|---|---|
| `db` | `postgres:16-alpine` | 5432 | healthcheck via `pg_isready` |
| `api` | built from `backend/Dockerfile` | 4000 (host port configurable) | waits for the db healthcheck, then `prisma migrate deploy` → `npm run seed` → `npm start` |
| `web` | built from `frontend/Dockerfile` | 3000 | `next start` against the baked-in `NEXT_PUBLIC_API_URL` |

The API container waits on the database's healthcheck (`condition:
service_healthy`) before migrating, so `docker compose up` is a single,
order-correct command - no "wait for Postgres then re-run" dance.

### Host port overrides

Host ports can collide with services already running on a machine (Windows
reserves ranges for Hyper-V/WinNAT, for example). Both published ports are
therefore overridable without editing the compose file:

```bash
# repo-root .env
API_HOST_PORT=4100     # default 4000
WEB_HOST_PORT=3000     # default 3000
```

Because Next.js inlines `NEXT_PUBLIC_*` at **build** time, the override has to
reach the web build as well - the compose `environment:` value alone does not do
it:

1. set `API_HOST_PORT=4100` in the repo-root `.env` (compose publishes the API
   there),
2. set `NEXT_PUBLIC_API_URL=http://localhost:4100` in `frontend/.env` (Next.js
   reads it when the bundle is built), and
3. rebuild the web image: `docker compose up -d --build web`.

Skipping step 2 produces a web app that builds and serves fine but calls port
4000 in the browser - a confusing failure, and exactly the one this escape hatch
exists to avoid. The committed `frontend/.env.example` keeps the default 4000,
so a normal `docker compose up --build` needs no thought.

## 2. Free-tier hosting (no payment required)

The API is a stateless Express process (JWT, no server-side session) and the web
app is a standard Next.js build, so any container host works. Every option below
has a free tier that is enough for a demo; Option A is the one this repo
automates.

### Option A - Render Blueprint (one click for the whole stack)

`render.yaml` at the repo root declares this deployment as code, so nothing has
to be wired by hand: Render reads the blueprint and creates a free Postgres
instance, the API web service and the web app, then redeploys all three on every
push.

<https://render.com/deploy?repo=https://github.com/Yarafat2001/dhaka-tesla-pool>

1. Open that link (or Render dashboard → **New** → **Blueprint**) and sign in
   with GitHub; it needs read access to `Yarafat2001/dhaka-tesla-pool`.
2. Accept the defaults and click **Apply**. Service names are globally unique on
   Render, so if `dhaka-tesla-pool-web` is taken Render appends a suffix - the
   URL it shows is the one that matters.
3. Wait for the first deploy (a few minutes: two Docker builds, then migrations
   and the seed on the API's first boot).
4. Copy the web service's URL (`https://<name>.onrender.com`) into the README's
   deployment section. That is the public "Live Project Link".

What it creates:

| Piece | Detail |
|---|---|
| `dhaka-tesla-pool-db` | free Postgres, region Singapore, `ipAllowList: []` so it is reachable over Render's internal network only |
| `dhaka-tesla-pool-api` | Docker, `backend/`, health check `/health`, `DATABASE_URL` from the database above, `JWT_SECRET` generated by Render |
| `dhaka-tesla-pool-web` | Docker, `frontend/`, health check `/`, `NEXT_PUBLIC_API_URL` resolved from the API service's host |

Two details that would otherwise bite:

- **The API URL and its scheme.** `fromService.property: host` resolves to a bare
  host with no `https://`, and `fetch()` treats a scheme-less URL as a path
  relative to the current page - the web app would call itself and every API
  request would 404. `frontend/lib/api.ts` therefore adds `https://` when the
  value has no scheme, and `frontend/Dockerfile` accepts it as a build ARG.
  Render passes a service's environment variables into its Docker build, which
  is what gets `NEXT_PUBLIC_API_URL` into `next build` - Next.js inlines it
  there, it is never read at runtime.
- **`PORT` is deliberately absent from the blueprint.** Render injects `PORT`
  and the API already reads `process.env.PORT` (`backend/src/index.ts`), so
  there is nothing to set; `EXPOSE 4000` in the backend Dockerfile is
  documentation only.

Free-tier behaviour to expect - which is why this repo commits the link rather
than a URL:

- Free web services **spin down after ~15 minutes idle**. The next request pays a
  cold start, and for the API that includes `prisma migrate deploy && npm run
  seed` before the port opens, so the first page load can take a minute or so.
  Reloading then hits a warm service.
- Free **Postgres expires 30 days after creation**. Render emails beforehand; to
  keep a demo alive past that, re-create the database (re-run the blueprint, or
  re-point `DATABASE_URL`) or move that piece to Neon (Option B).
- A cold start re-runs the seed. Every write in `seed.ts` is an upsert, so this
  is idempotent: demo wallets reset to ৳500.00 instead of drifting.

### Option B - Render by hand, with Neon Postgres

The same shape as the blueprint, for when the database should live outside
Render:

1. Create a free Postgres database at <https://neon.tech> and copy its
   connection string (append `?schema=public`).
2. On Render, create a **Web Service** from this repo:
   - Runtime: Docker, root directory `backend`, Dockerfile path `./Dockerfile`
   - Environment variables: `DATABASE_URL` = the Neon connection string,
     `JWT_SECRET` = a long random string (never commit it). Leave `PORT` alone -
     Render supplies it.
   - Health check path: `/health`
   - The container runs `prisma migrate deploy && npm run seed && npm start`, so
     the schema and demo data are provisioned on first boot.
3. Create a second **Web Service** for the frontend:
   - Runtime: Docker, root directory `frontend`, Dockerfile path `./Dockerfile`
   - Environment variable `NEXT_PUBLIC_API_URL` = the API's host prefixed with
     `https://` (it must be set **before** the build, because Next.js inlines it;
     Render rebuilds when an env var changes).
4. Note the two public URLs in the README's deployment section.

Both free tiers sleep when idle; the first request after a sleep takes a few
seconds. That is acceptable for a demo and free of charge.

### Option C - Fly.io

```bash
fly launch --dockerfile backend/Dockerfile --name dhaka-tesla-pool-api
fly secrets set DATABASE_URL="<neon-or-fly-postgres-url>" JWT_SECRET="<random>"
fly deploy
```

Fly's free allowance changes over time, and Postgres is not free by default - if
it is no longer free, use Neon (Option B) for the database and keep the API on
Fly/Render. This is exactly the kind of "read the current pricing page before
committing" check worth doing rather than assuming.

## 3. Environment variables

| Variable | Where | Purpose |
|---|---|---|
| `DATABASE_URL` | backend | Postgres connection string |
| `JWT_SECRET` | backend | signs/verifies JWTs - set a long random value in any real deployment |
| `PORT` | backend | API port. Locally it defaults to 4000; on Render, Render injects it - do not set it by hand |
| `NEXT_PUBLIC_API_URL` | frontend | API base URL, inlined at **build** time - pass it as `--build-arg` (Render) or put it in `frontend/.env` (compose), and rebuild after changing it. A bare host with no scheme is accepted and treated as `https://<host>` |
| `API_HOST_PORT` / `WEB_HOST_PORT` | repo root (compose only) | host port overrides |

Real secrets never belong in the repo: `backend/.env` and `frontend/.env` are
gitignored, and only the `.env.example` files are committed.

## 4. Verifying a deployment

```bash
curl https://<api-host>/health            # {"status":"ok"}
curl https://<api-host>/api/zones         # the seeded Dhaka zones
```

Then sign in on the web app as Nusrat (`01710000002` / `password123`) and request
Banani → Mohakhali, and as Jashim (`01710000001`) to accept and complete the trip.

On a free Render instance, a request that arrives after the service has been idle
is the one that wakes it: that first call includes the container start, the
migrations and the seed, so give it a retry rather than reading a timeout as a
broken deployment. Logins are seeded (all passwords `password123`), so a "user
not found" would mean the seed did not run - check the API service's logs for
`Seed complete.` and the four demo accounts.

## 5. Not done here, and why

- No public URL is committed anywhere in the repo: provisioning one needs an
  account with a hosting provider, which is the single step that cannot be
  automated from inside the repo. What is committed is everything up to that
  click - `render.yaml` - so the deployment is reproducible rather than
  hand-driven, and the README carries the blueprint link plus the place to paste
  the resulting URL.
- No paid infrastructure was used for this challenge, per Section 16.
- No Kubernetes, autoscaling or managed queues: at this scale they would add
  moving parts without evidence they are needed (Section 9). What would change at
  real scale is reasoned through in `docs/scaling-bonus.md`.
